Overview

Build SwiftSER, a read-only SER file parser in Swift. SER is a simple container used by planetary and solar astro-imaging capture software: a fixed 178-byte header, a run of raw uncompressed image frames, and an optional trailer of per-frame UTC timestamps. The library exposes the header metadata, per-frame timestamps, and random access to individual frames' pixel data — then, on Apple platforms, converts frames to CGImage and encodes whole sequences into playable QuickTime movies.

The architecture, naming, file organization, documentation style and test approach follow the SwiftFITS project as closely as the format allows: a top-level file type owning parsed sub-objects, an OptionSet of parsing options with .strict/.lenient presets, a single LocalizedError enum, full doc comments on public and private members, and a broad Swift Testing suite with one test file per source file plus an integration suite. The core parser stays Foundation-only so it remains portable; everything that needs Accelerate, CoreGraphics or AVFoundation lives in separate files behind #if canImport(…) guards, within the single SwiftSER target.

Questions & answers

SwiftFITS is strictly Foundation-only and documented as Linux-portable. SER image/movie export needs CoreGraphics + AVFoundation. How should that be structured?
One target, guarded imports. A single SwiftSER product, as in SwiftFITS. The parser stays Foundation-only; imaging and movie code live in separate files behind #if canImport(AVFoundation) / #if canImport(CoreGraphics) / #if canImport(Accelerate). One module for consumers, portable core.
SwiftFITS does both reading and writing (build from scratch, serialize, byte-for-byte round-trip). What scope for SwiftSER?
Read-only. Parse the header, frames and trailer; expose metadata and frame data; export images and movies. No SER writing, no serialization, no round-trip requirement.
Should the library include debayering, and what data format should it use?
Yes — its own, complete implementation. SwiftSER defines its own SERBayerPattern enum covering all SER patterns, and ships an Accelerate-backed debayering process handling every one of them (including the CMY patterns), so that used as-is the library can always produce a result. The pixel data format is interleaved [Double], row-major, non-normalized (raw stored sample values, not scaled to 0...1).
Should debayering be delegable to the consumer?
Yes. A consumer can install its own debayering implementation. It can signal that it does not support a given pattern, in which case SwiftSER falls back to its own implementation. It can also throw to indicate an error, with a configurable policy deciding whether that falls back to the built-in implementation or propagates to the caller.
The CMYG patterns (ColorID 16–19) have no spec-defined conversion to RGB — real sensors need a per-sensor matrix. Should they be excluded from color output?
No — they must be handled. The library must always be able to produce a result when used as-is. The plan therefore implements CMY debayering with the complementary-color decode (see Appendix — CMY to RGB), documented as an approximation that ignores real sensor spectral overlap.
Is a dependency on the existing SwiftPixel pixel-processing library acceptable?
No. SwiftPixel cannot be a dependency of SwiftSER. It was consulted only to settle the pixel data format (interleaved [Double], non-normalized), so that a consumer already using it can plug its debayering in through the delegation hook with a trivial adapter. SwiftSER neither imports it nor mirrors its API.

Notes

Format facts driving the design

All of the following are taken directly from SER Doc V3b.pdf and were verified against the PDF text.

FactConsequence for the implementation
Header is a fixed 178 bytes; image data starts at offset 178. No block/chunk structure as in FITS. Parsing is a flat field decode at fixed offsets.
All integer header fields are little-endian Integer_32 / Integer_64 (v3 clarification; v2 did not state it). Header decode is unconditionally little-endian, independent of field 4.
Field 4 LittleEndian governs byte order of 16-bit image data only: 0 = big-endian, 1 = little-endian. Frame decode is parameterized on this flag; header decode is not. Note the field name is the inverse of what a naive reading suggests for the 0 case.
NumberOfPlanes is 1 for ColorID 0–19 (MONO and all Bayer), and 3 for RGB (100) / BGR (101). Bayer frames are single-plane mosaics — debayering is the library's job, not the format's.
BytesPerPixel = 1 × NumberOfPlanes for PixelDepthPerPlane 1–8, 2 × NumberOfPlanes for 9–16. Frame size = width × height × BytesPerPixel; drives both frame offsets and trailer offset.
Samples of 1–8 bits are stored MSB-aligned; samples of 9–16 bits are stored LSB-aligned. Asymmetric normalization. A 12-bit sample occupies 0–4095 of a 16-bit container and renders nearly black unless scaled; a 5-bit sample is already left-shifted toward full scale.
Strings (Observer, Instrument, Telescope) are 40 bytes, ASCII 32–126, unused bytes filled with 0. Trim on NUL and validate the printable range; leniency flag for out-of-range bytes.
Timestamps are 64-bit tick counts of 100 ns since 0001-01-01 00:00:00 (.NET DateTime). Reportedly only 62 bits are meaningful (Behrend); the two MSBs are undocumented. Needs a dedicated conversion to Date, with a documented epoch offset and a leniency flag for the high bits.
If DateTime <= 0, it is invalid and the file has no timestamp trailer. Trailer presence is derived from the header field plus the actual file length, not assumed.
Trailer starts at 178 + FrameCount × Width × Height × BytesPerPixel and holds one 64-bit UTC timestamp per frame. Trailer size is 8 × FrameCount; a short or absent trailer is a leniency case.
Spec version discrepancy. V2 field 7 is PixelDepth with BytesPerPixel 1 or 2; V3 renames it PixelDepthPerPlane and multiplies by NumberOfPlanes. V2 also lacks RGB/BGR (100/101) and states no endianness for header fields. The library implements V3, which is a strict superset for every file V2 could describe — a V2 file has NumberOfPlanes == 1, so the two definitions of BytesPerPixel agree.

Accelerate: what was verified

Checked against the macOS 26.5 SDK headers, not assumed:

  • vImage has no demosaic function at all — a search of every vImage header for demosaic/debayer/bayer returns nothing.
  • vImage has no double-precision pixel buffer. Pixel_F is float (vImage_Types.h:272); convolution exists only as vImageConvolve_Planar8, _Planar16F, _PlanarF. Using vImage would force a Double → Float → Double round-trip.
  • vDSP does have everything needed, natively in double precision — vDSP_f3x3D (3×3 convolution, vDSP.h:2345), vDSP_f5x5D (2359), vDSP_imgfirD (2407), plus vDSP_vfltu8D (5290) and vDSP_vfltu16D (5304) for integer→double conversion.

This is what makes an Accelerate-backed [Double] debayer practical: bilinear demosaicing is a 3×3 convolution per channel over a masked mosaic, which maps directly onto vDSP_f3x3D. See Appendix — Bilinear kernels.

Conventions to follow

  • MIT header block on every file, Copyright (c) 2026, Jean-David Gadina - www.xs-labs.com.
  • One type per file; subfolders for grouping (Imaging/, Video/, Extensions/).
  • Explicit public throughout the library target; internal/private only for genuine implementation details.
  • SwiftDoc (///) comments on every type and member — public, internal and private alike — with - Parameters:/- Returns:/- Throws:, matching SwiftFITS, where even private helpers carry full documentation.
  • Documentation is written with the code, in every milestone — not retrofitted. Milestone 9 verifies coverage; it is not where documentation gets written.
  • No force-unwrap. let over var. Early returns. Aligned = signs. Blank line between calls and assignments.
  • Prefer map/filter/reduce/forEach over raw loops — except in the pixel inner loops, where an explicit indexed loop or an Accelerate call is the correct choice and should carry a comment saying why.
  • Swift Testing (@Test, #expect, #require), one test file per source file, plus Integration.swift.
  • The Xcode project and Package.swift must be kept in sync.
Two build systems, both of which must stay green. The repository already ships an Xcode project with a SwiftSER framework target and a SwiftSERTests test target, and a Package.swift. Both must build and test at every milestone — .github/workflows/ci-mac.yaml already enforces this, with an xcodebuild job that builds and analyzes both Debug and Release but runs tests in Debug only (test: 0 for Release), plus a separate spm job running swift build / swift test in both configurations. A Release-only test failure is therefore caught by the SPM job alone — another reason not to treat either system as standing in for the other.

The failure mode is asymmetric and easy to miss: the SPM targets are path-based (path: "SwiftSER" / path: "SwiftSERTests"), so a new source file is picked up automatically, while the Xcode project needs it added explicitly with the right target membership. A file that compiles under swift build can therefore be silently absent from the framework — so every milestone registers its files in the Xcode project and verifies through both systems, rather than assuming one implies the other.
Prerequisite for Milestone 9. The source document states test files can be provided on demand. Real .ser captures are needed to validate against the wild — ideally a mono 8-bit, a mono 16-bit, an RGB Bayer 16-bit, and one without a timestamp trailer. They belong in a tracked Test Files directory at the repository root, matching SwiftFITS. Until they exist, that milestone runs on synthetic fixtures only.

Implementation notes

Implemented test-first. Each behavior was pinned by a test that was run and observed to fail — in Swift the red phase is the compiler rejecting the test because the API does not exist yet — before the implementation was written. The suite went from 22 to 23 tests over the milestone; all of them pass.

Files created

  • SwiftSER/SERError.swift — the twelve cases the plan lists, shaped after FITSError: LocalizedError, CustomStringConvertible, Sendable, with the "SER Error: …" prefix on description. Payloads were chosen to match the format rather than the call site: unsupportedColorID and unsupportedPixelDepth carry Int32, mirroring the header's Integer_32 fields, while frameIndexOutOfRange carries Int index and count, since that is an API-boundary concern.
  • SwiftSER/SERParsingOptions.swift — the eight leniency flags on bits 0–7. Unlike FITSParsingOptions, SER has no "spec convenience" options to reassemble multi-record values, so .strict is the empty set and .lenient is all eight flags.
  • SwiftSER/Extensions/Data.swift — integer(_:at:littleEndian:) and slice(at:count:).
  • SwiftSERTests/SERError.swift, SwiftSERTests/SERParsingOptions.swift, SwiftSERTests/Data.swift — one test file per source file.
  • SwiftSER.xctestplan — mirroring SwiftFITS.xctestplan, referenced from the shared scheme, which previously carried shouldAutocreateTestPlan = "YES".

Decisions

  • Integer decoding combines bytes explicitly rather than reinterpreting memory in place, so no offset alignment is required and the result never depends on the host's byte order. It relies on Swift's << being a total "smart shift" that discards overflowing bits instead of trapping, which is exactly right for a signed type whose stored high bit is set — verified by test (0x00000080 little-endian decodes to Int32.min) and independently by both reviewers.
  • Offsets are relative to the receiver's startIndex, not to index zero, so a Data slice reads identically to standalone data holding the same bytes. Two tests pin this; Milestone 4 will hand frame slices to these methods.
  • The subrange helper returns a slice, not a copy, so slicing a memory-mapped multi-gigabyte capture does not touch the underlying pages. It is named slice(at:count:) rather than subdata(at:count:) precisely because Foundation's subdata(in:) has the opposite semantics (it copies and rebases to zero) — see the automated review below.
  • Bounds checks throw instead of trapping, and offset + count goes through addingReportingOverflow so a wrapped range can never look valid. Negative offsets and counts are rejected before the arithmetic.
  • Only Extensions/ was created, not Imaging/ and Video/. Git cannot track empty directories and an empty Xcode group is noise; Milestones 6 and 7 create them with their first file.

Verification

Both build systems, both configurations, at the end of the milestone: swift test Debug and Release — 23 tests, all pass; xcodebuild Debug — BUILD SUCCEEDED / TEST SUCCEEDED; xcodebuild Release — BUILD SUCCEEDED / ANALYZE SUCCEEDED. Both reviewers independently re-ran all four and confirmed. One of them also compiled an external consumer against the built .framework to prove the Xcode target membership is correct end to end, and fuzzed integer(_:at:littleEndian:) against the standard library's T(littleEndian:)/T(bigEndian:) over 200 000 random vectors per integer type at both optimization levels, with zero mismatches.

Milestone 2 — Header parsing Not started

Goal

Decode the fixed 178-byte header into a fully typed, documented value, with every field validated and every derived quantity (planes, bytes per pixel, frame size) computed once and exposed. This is the foundation for frame addressing, so its arithmetic must be overflow-safe.

Tasks
  • Create SERColorID.swift — the raw Int32 ColorID as an enum: mono (0), the four RGB Bayer patterns (8–11), the four CMY Bayer patterns (16–19), rgb (100), bgr (101). Expose numberOfPlanes and an isBayer flag. Preserve unrecognized values under allowUnknownColorID.
  • Create SERBayerPattern.swift — rggb, grbg, gbrg, bggr, cyym, ycmy, ymcy, myyc, with a description giving the four-letter code, an isCMY flag, and the 2×2 tile layout used by the debayer. Derived from SERColorID.
  • Create SERHeader.swift — all 13 fields, decoded little-endian at fixed offsets: fileID, luID, colorID, isLittleEndian, imageWidth, imageHeight, pixelDepthPerPlane, frameCount, observer, instrument, telescope, dateTime, dateTimeUTC.
  • Expose the derived geometry: numberOfPlanes, bytesPerPixel, bytesPerFrame, bayerPattern, and a hasTimestampTrailer flag from dateTime > 0. Use multipliedReportingOverflow throughout and throw on overflow rather than trapping.

  • Implement 40-byte string decoding: NUL-trim, printable-range validation, leniency fallback.
  • Add CustomStringConvertible to SERHeader, following FITSSection.description's style.
  • Register files in the Xcode project.
  • Write SERHeader, SERColorID and SERBayerPattern unit tests from synthetic 178-byte headers: every ColorID, both endianness values, every depth boundary (1, 8, 9, 16), each validation failure under strict and its leniency counterpart, and overflow-inducing geometry.

Phase 2 — Pixel data

Milestone 4 — Raw frame access and sample decoding Not started

Goal

Expose individual frames and decode their samples correctly — the part of the format most likely to be got subtly wrong. This milestone owns the three traps: MSB versus LSB bit alignment, the header-driven byte order for 16-bit data, and the fact that 16-bit SER samples are unsigned.

Tasks
  • Create SERFrame.swift — a frame view holding its index, its slice of the file's data, and a reference to the header. Provides the raw bytes untouched, plus its timestamp when available.
  • Implement sample decoding to [Double], interleaved, row-major, non-normalized: 8-bit samples widened directly; 16-bit samples byte-swapped per the header's LittleEndian field and widened as unsigned.
  • Implement bit-alignment handling: for pixelDepthPerPlane 1–8 the sample is MSB-aligned within its byte; for 9–16 it is LSB-aligned within its 16-bit container. Expose the true value range (0...(2^depth - 1) for the LSB-aligned case) so later stages can scale correctly.
  • Add SERFrame.samples for the decoded [Double] and SERFrame.rawData for the untouched bytes. Keep decoding lazy so enumerating frames costs nothing until samples are requested.
  • Handle the BGR channel order (ColorID 101) by reordering to RGB during decode, so everything downstream sees RGB.
  • Add frame access on SERFile: frame(at:), a frames lazy collection, and Sequence conformance for iteration.
  • Use Accelerate for the widening when available (vDSP_vfltu8D / vDSP_vfltu16D). Keep the plain-Swift implementation always compiled — only the Accelerate one is wrapped in #if canImport(Accelerate) — with an internal selector so tests can force either path. Guarding both would leave the fallback never compiled or tested on macOS, where the import always succeeds.
  • Register files in the Xcode project.
  • Write SERFrame unit tests: every depth boundary (1, 8, 9, 12, 16), both byte orders, MONO/RGB/BGR channel handling, unsigned 16-bit values above 32767 decoding positive, out-of-range indices, and Accelerate/scalar path equivalence.
  • Verify: xcodebuild build + test and swift build / swift test.

Milestone 5 — Debayering: patterns, built-in implementation and delegation Not started

Goal

Turn single-plane Bayer mosaics into 3-channel RGB. SwiftSER ships a complete, Accelerate-backed bilinear implementation covering all eight SER Bayer patterns — RGB and CMY alike — so the library always produces a result on its own. A consumer with a better implementation can take over, decline individual patterns, or fail, with SwiftSER's own implementation as the safety net.

Tasks
  • Create SERDebayering.swift — the delegation protocol: 
    public protocol SERDebayering
{
    /// Whether this implementation handles the given pattern. When `false`,
    /// SwiftSER uses its own built-in implementation instead.
    func supports( pattern: SERBayerPattern ) -> Bool

    /// - Parameter mosaic: single-plane, row-major, non-normalized samples
    /// - Returns: interleaved RGB, row-major, `width * height * 3` samples
    func debayer( mosaic: [ Double ], width: Int, height: Int, pattern: SERBayerPattern ) throws -> [ Double ]
}
  • Create SERDebayerFailurePolicy.swift — fallBackToBuiltIn (default) or propagate, deciding what happens when a delegate throws. A delegate returning false from supports(pattern:) always falls back, regardless of policy — declining is not an error.
  • Create SERBilinearDebayering.swift — the built-in implementation, conforming to the same protocol and reporting true for every pattern.
  • Implement the RGB path: build three masked planes from the pattern's 2×2 tile, convolve each with its bilinear kernel (Appendix), and interleave. Use vDSP_f3x3D when Accelerate is available, keeping the equivalent plain-Swift convolution always compiled and selectable, as in Milestone 4.
  • Implement the CMY path: interpolate the C/Y/M planes with the same kernels (yellow is the twice-sampled channel, as green is in RGB Bayer), then apply the complementary-color transform (Appendix) as a 3×3 matrix multiply. Document it prominently as an approximation that ignores real sensor spectral response.
  • Handle edges by clamping coordinates to the image bounds, so border pixels interpolate from the same colors interior pixels would see.
  • Wire delegation into SERFile: a debayering: SERDebayering? property and a debayerFailurePolicy property, both defaulting so the library works untouched.
  • Ensure MONO (ColorID 0) bypasses debayering entirely and RGB/BGR (100/101) are already 3-channel — neither goes through this path.
  • Register files in the Xcode project.
  • Write debayering unit tests: each of the eight patterns against hand-computed expected output on a small synthetic mosaic; edge/corner correctness; a delegate that is used; one that declines via supports; one that throws under each failure policy; Accelerate/scalar equivalence; and geometry-mismatch errors.
  • Verify: xcodebuild build + test and swift build / swift test.

Bilinear demosaic kernels

Bilinear demosaicing is a per-channel 3×3 convolution over a masked mosaic: build a plane holding each site's sample where its filter matches the channel and zero elsewhere, then convolve. Red and blue are sampled once per 2×2 tile, green (or yellow, for CMY) twice — hence the two kernels: 

Red / Blue          Green / Yellow
(sampled 1 per      (sampled 2 per
 2x2 tile)           2x2 tile)

1/4 * [ 1 2 1 ]     1/4 * [ 0 1 0 ]
      [ 2 4 2 ]           [ 1 4 1 ]
      [ 1 2 1 ]           [ 0 1 0 ]

Both map directly onto vDSP_f3x3D. Coordinates are clamped to the image bounds so border sites interpolate from the same color arrangement interior sites would see.

CMY to RGB conversion

The CMY Bayer tiles hold cyan, yellow and magenta samples, with yellow appearing twice per tile. Complementary color filters relate to additive primaries as: 

C = G + B
Y = R + G
M = R + B

Solving that system for the additive primaries gives:

R = ( Y + M - C ) / 2
G = ( C + Y - M ) / 2
B = ( C + M - Y ) / 2
This is an approximation. It assumes ideal, non-overlapping filter responses. Real CMYG sensors have substantial spectral overlap and need a per-sensor calibration matrix, which the SER format does not record and the specification does not define. Colors produced from ColorID 16–19 are therefore plausible but not colorimetrically accurate, and the public documentation must say so. Results are clamped to the valid range, since the transform can produce out-of-range values on noisy input.

Bit alignment

The specification's alignment rules are asymmetric, and getting this wrong produces images that are either too dark or subtly quantized:

DepthContainerAlignmentExampleStored range
1–88-bitMSB5-bit → bbbbb000Already near full scale
9–1616-bitLSB12-bit → 0000bbbbbbbbbbbb0...4095 of 0...65535

The 9–16 bit case is why image and movie output scale by default: handing a 12-bit frame to CoreGraphics untouched renders it at roughly 6% brightness.

Delegating debayering to an external library

SwiftSER has no dependencies, so a consumer wanting to use its own debayering supplies an adapter. Using SwiftPixel as an example — a library working on interleaved, non-normalized [Double] buffers, which is why SwiftSER adopted that same currency: 

import SwiftPixel
import SwiftSER

struct PixelDebayering: SERDebayering
{
    func supports( pattern: SERBayerPattern ) -> Bool
    {
        pattern.isCMY == false // SwiftPixel implements the four RGB patterns
    }

    func debayer( mosaic: [ Double ], width: Int, height: Int, pattern: SERBayerPattern ) throws -> [ Double ]
    {
        var buffer = try PixelBuffer( width: width, height: height, channels: 1, pixels: mosaic, isNormalized: false )

        try Processors.Debayer( mode: .vng, pattern: pattern.pixelPattern ).process( buffer: &buffer )

        return buffer.pixels
    }
}

The pattern mapping lives in the consumer's code, since SwiftSER cannot reference an external library's types: 

extension SERBayerPattern
{
    var pixelPattern: Processors.Debayer.Pattern
    {
        switch self
        {
            case .rggb: return .rggb
            case .grbg: return .grbg
            case .gbrg: return .gbrg
            case .bggr: return .bggr
            default:    return .rggb // unreachable: declined by supports(pattern:)
        }
    }
}

Declining the CMY patterns through supports(pattern:) means SwiftSER transparently handles those four with its own implementation, so the consumer still gets a result for every file.
